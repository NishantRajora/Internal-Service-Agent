========================================
PROJECT OVERVIEW
================

Project Name: Veridian Corp AI IT Support Agent
Description: A full-stack agentic AI system designed to automate first-line IT support for Veridian Corp. The system utilizes a RAG (Retrieval-Augmented Generation) pattern to ensure AI responses are grounded in official company policies. It integrates an automated ticketing system and a secure admin dashboard for oversight.

Core Objectives:
1. Automate IT request classification and resolution.
2. Ensure consistency through historical ticket analysis.
3. Reduce human workload by resolving simple issues via self-service.
4. Provide a secure audit trail of all AI decisions.

========================================
FRONTEND ARCHITECTURE
=====================

The frontend is a Single Page Application (SPA) structure.
- Layout: Tabbed navigation allowing users to switch between 'Support', 'My Tickets', and 'Admin'.
- State Management: Managed via JavaScript variables (e.g., `adminToken`) and DOM manipulation.
- Communication: Asynchronous `fetch` API calls to the FastAPI backend.
- Key Components:
    - Chat Interface: Real-time request submission and AI response display.
    - Ticket Grid: Visual representation of employee tickets using status badges.
    - Admin Dashboard: Table-based view for audit logs, tickets, and knowledge base.
    - Status Modal: Professional UI for admins to update ticket statuses.

========================================
BACKEND ARCHITECTURE
====================

The backend is a RESTful API built with FastAPI.
- Routing: Centralized in `main.py`.
- Logic Separation:
    - Request Handling $\rightarrow$ `main.py`
    - AI Orchestration $\rightarrow$ `agent.py`
    - Data Retrieval $\rightarrow$ `retriever.py`
    - Data Persistence $\rightarrow$ `database.py`
- Security: Admin endpoints are protected by a dependency `verify_admin_token` which checks for a valid Bearer token.
- Session Handling: Simple in-memory dictionary `SESSION_TOKENS` stores active admin sessions.

========================================
AI AGENT ARCHITECTURE
=====================

The agent follows a strict agentic pipeline to avoid hallucinations and ensure policy compliance.

COMPONENT: Request Classifier
FILE: agent.py
FUNCTION: classify_request()
HOW IT WORKS: Sends the user request to the LLM with a list of valid IT categories.
INPUT: User request string
OUTPUT: Category name (e.g., "VPN Access")
USED BY: process_request()

COMPONENT: Knowledge Retriever
FILE: retriever.py
FUNCTION: find_relevant_policy()
HOW IT WORKS: Maps the category to a policy ID or calculates a keyword score against the knowledge base.
INPUT: Category, User request
OUTPUT: Policy object from policies.json
USED BY: process_request()

COMPONENT: Decision Engine
FILE: agent.py
FUNCTION: make_decision()
HOW IT WORKS: Combines the Policy, User Request, and Historical Precedents into a prompt for the LLM.
INPUT: Category, Request, Policy, Historical Context
OUTPUT: JSON object {status, action, needs_ticket, reason, follow_up}
USED BY: process_request()

COMPONENT: Response Generator
FILE: agent.py
FUNCTION: generate_response()
HOW IT WORKS: Synthesizes the final employee-facing message based on the decision and policy.
INPUT: Employee name, Request, Category, Policy, Decision, Ticket ID
OUTPUT: Professional text response
USED BY: process_request()

========================================
AGENT DECISION LOGIC
====================

The agent decides actions based on "Ground Truth" (Policies) and "Consistency" (History).

BRANCH EXAMPLE: VPN Request
- TRIGGER: User asks for VPN access.
- POLICY: KB-02 (VPN Access).
- AGENT DECISION:
    - If Full-time employee $\rightarrow$ Resolved (Automatic).
    - If Contractor $\rightarrow$ Escalated (Requires Manager Approval).
- TOOL/API: If Escalated $\rightarrow$ `database.create_ticket()`.
- RESULT: Response informing the user of the outcome.
- FILE: agent.py

BRANCH EXAMPLE: Security Incident
- TRIGGER: User reports phishing.
- POLICY: KB-09 (Security Incident Reporting).
- AGENT DECISION: Always set `needs_ticket: true` for high-risk issues.
- TOOL/API: `database.create_ticket()`.
- RESULT: Immediate escalation to Security Team.
- FILE: agent.py

BRANCH EXAMPLE: Guest Wi-Fi
- TRIGGER: Request for visitor Wi-Fi.
- POLICY: KB-07 (Guest Wi-Fi Access).
- AGENT DECISION: set `needs_ticket: false`.
- RESULT: Instructions to use the front-desk kiosk.
- FILE: agent.py

========================================
RAISE TICKET WORKFLOW
=====================

USER ACTION: User submits request "My laptop is broken"
↓
FRONTEND FILE: static/script.js -> sendRequest()
↓
API ENDPOINT: /api/support/request (POST)
↓
BACKEND FILE: main.py -> handle_request()
↓
AGENT LOGIC: agent.py -> process_request()
    - classify_request() -> "Laptop / Hardware"
    - find_relevant_policy() -> KB-03
    - make_decision() -> { needs_ticket: true, status: "Escalated", ... }
↓
TICKET CREATION LOGIC: database.py -> create_ticket()
    - Generates ID (e.g., AUTO-015)
    - Sets fields: employee, email, issue, category, action, policy_id, status, created_at
↓
STORAGE: SQLite (tickets table)
↓
RESPONSE: JSON containing response text and ticket object {ticket_id: "AUTO-015", ...}
↓
UI: script.js -> appendMessage() (Displays "Ticket AUTO-015 has been created")

========================================
TICKET SYSTEM
=============

- Data Source: SQLite (`veridian_it.db`).
- Schema: tickets (ticket_id, employee, email, issue, category, action, policy_id, status, created_at).
- ID Format: `AUTO-XXX` (Sequential).
- Statuses: Resolved, Escalated, Follow-up Required, Closed, Pending.
- Creation: Automatic via AI Agent if `needs_ticket` is true.
- Updating: Manual via Admin Dashboard (PATCH request).
- History: Tracked via the `audit_logs` table.
- Implementation: Dynamic database (not static JSON).

========================================
LLM / AI TECHNOLOGIES
=====================

- Technology: Ollama
- Model: gpt-oss:20b
- Pattern: RAG (Retrieval-Augmented Generation)
- Prompting: System-level prompts for Classification, Decision, and Response generation.
- Output Format: JSON (enforced via `format: "json"` in Ollama call).
- RAG Mechanism: Keyword-based lookup in `policies.json`.

========================================
PROMPTS
=======

- Classification Prompt: "You are an IT support classifier... Classify the user's request into exactly one of these categories... Return result as JSON."
- Decision Prompt: "You are the Decision Engine... Use the provided Policy as the primary ground truth... If the user explicitly asks to 'create a ticket'... you MUST set needs_ticket to true."
- Response Prompt: "You are a polite and professional IT Support Agent... Write a response to the employee based on the provided decision and policy."

========================================
HUMAN ESCALATION
================

Human escalation is triggered when the AI Agent determines that a request cannot be solved via self-service.
- Condition: `needs_ticket` set to `true` by the Decision Engine.
- Action: A record is created in the `tickets` database table.
- Visibility: The ticket appears in the Admin Dashboard for human IT staff to review and manually update the status to 'Resolved' or 'Closed'.

========================================
SECURITY
========

- Admin Access: Protected by hashed passwords (Bcrypt) and Bearer tokens.
- Data Protection: API endpoints for tickets and audit logs require `verify_admin_token` dependency.
- Input Validation: Pydantic models used in FastAPI for type checking (`SupportRequest`, `LoginRequest`).

========================================
ERROR HANDLING
==============

- API Errors: FastAPI `HTTPException` used to return 401 (Unauthorized), 404 (Not Found), and 500 (Internal Server Error).
- Agent Errors: Try-except blocks in `process_request` and `call_ollama` to prevent server crashes on AI failures.
- Frontend Errors: `try-catch` blocks around `fetch` calls with user-facing alerts.
- Database Errors: Basic error handling in `database.py` and `seed_tickets.py`.

========================================
COMPLETE SOLUTION ARCHITECTURE
==============================

The solution is a "Grounded AI Agent".
1. The User interacts with a Frontend.
2. The Backend acts as a Controller.
3. The Agent acts as the Orchestrator.
4. The Knowledge Base (JSON) acts as the source of truth.
5. The LLM (Ollama) provides the reasoning capability.
6. The SQLite Database provides persistence and auditability.

This ensures that the AI does not "make up" policies, as it is forced to retrieve a policy first and use it as the basis for its decision.

========================================
END-TO-END PROCESS FLOW
=======================

[User] $\rightarrow$ [Frontend: index.html] $\rightarrow$ [Backend: main.py] $\rightarrow$ [Agent: agent.py] $\rightarrow$ [Retrieval: retriever.py] $\rightarrow$ [KB: policies.json] $\rightarrow$ [LLM: Ollama] $\rightarrow$ [Decision: agent.py] $\rightarrow$ [Storage: database.py] $\rightarrow$ [Response: agent.py] $\rightarrow$ [Frontend: script.js] $\rightarrow$ [User]

========================================
LIMITATIONS
===========

- LLM Dependency: Requires Ollama to be running locally.
- Session Management: Admin tokens are in-memory and lost on server restart.
- Retrieval: Keyword-based retrieval is simple; would benefit from vector embeddings for complex queries.
- Concurrency: SQLite is used; not suitable for extremely high-volume concurrent writes.
